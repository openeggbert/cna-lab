# 29. Save games, checkpoints, profiles, and migration

[Back to master plan](../plan.md)

Persist logical state safely across district transitions, version changes, and interrupted writes.

- [x] **IG-29-001 P0** — Version the current save format and add explicit migration infrastructure. *(`kMinSaveFormatVersion`/`kCurrentSaveFormatVersion` in `SaveGame.hpp`; the first line is `format=iron-gang-save-v<N>`, parsed and range-checked. Below the minimum is refused, **above** the current version is refused by name ("written by a newer version of Iron Gang (format v3; this build understands up to v2)") rather than half-read for the fields that happen to parse. Version 1 files still load and are converted on read -- `mission_state`'s int index becomes `mission_state_id` through the exact table the deleted enum had -- and `SaveReadDiagnostics::formatVersion` reports which version the file was, so the game can log that it migrated one. The per-version **registry** of migration functions is IG-29-026 and is deliberately not built for two versions; `docs/save-format.md` documents when to add it. Verified by `TestSaveFormatRobustness` and `TestSaveMigratesLegacyMissionState`.)*
- [x] **IG-29-002 P0** — Implement atomic write to a temporary file followed by replacement. *(`SaveGame::Write` builds the whole document, writes it to `TemporaryPath()` (`<path>.tmp`), rotates any existing save to the backup, then renames the temporary into place -- both renames are within one directory, so both are atomic. A crash or a failed write leaves the previous save intact where it was or as the backup, never a half-written file at the save's own path; an exception mid-write removes the temporary. A leftover temporary from an interrupted run is ignored on read and replaced by the next write. Covered by `TestSaveFormatRobustness`, including a read-only-directory case standing in for a full disk, which asserts the existing save is left byte-for-byte intact.)*
- [x] **IG-29-003 P0** — Keep at least one rolling backup. *(Every write rotates the previous save to `SaveGame::BackupPath()` (`<path>.bak`) before the new one lands. `Read()` falls back to it when the primary file is missing, corrupt, or unsupported, and reports that through `SaveReadDiagnostics::usedBackup`/`primaryError`; `IronGangGame::LoadPrototype` logs the reason and shows "Loaded backup save" rather than recovering silently, since the player has lost whatever happened between the two. One generation only -- deeper history is IG-29-036's rotation work.)*
- [x] **IG-29-004 P0** — Add checksum/corruption detection. *(Format version 2's second line is `checksum=<FNV-1a 64-bit hex>` over every byte after it. A truncated, torn, or edited file fails to load rather than loading partially. Deliberately not a cryptographic hash and documented as such: it detects damage, it does not prevent editing -- a hand-edited save just needs its checksum recomputed, or the header dropped to v1. Missing required fields are also reported by name (`Save file is missing "player_position"`) instead of surfacing as a parse exception. Covered by `TestSaveFormatRobustness` (flipped byte, truncation, missing checksum line).)*
- [x] **IG-29-005 P0** — Separate user settings from campaign save data. *(Three files, three lifetimes, three owners: `runtime/settings.json` is what the **player** changes (`UserSettings`, `include/IronGang/Persistence/UserSettings.hpp`) and must survive deleting every save; `runtime/iron_gang_prototype.save` is campaign progress; `assets/config/game.json` is read-only developer tuning shipped with the game. Settings are written the moment one changes, atomically with a backup through the shared `WriteTextFileAtomically` (extracted from `SaveGame`, which had the only copy -- the second caller is where a pattern becomes shared or becomes two subtly different implementations). A missing settings file is normal and silent; bad values warn and keep defaults; an unsupported version fails and leaves the caller's settings untouched; the file inherits the bounded JSON read (plan_36 IG-36-002/009). Covered by `TestUserSettingsRoundTripAndFallBack`, including the read-only-directory case proving a failed write leaves the previous file intact.)* *(Partial by construction: developer tuning now lives in `assets/config/game.json` (plan_04 IG-04-001), which is read-only, never written back, and entirely separate from the save files. What is still missing is the other half -- **user** settings the player changes in game (audio volume, input bindings, display options), which have no system yet (plan_28's menus) and therefore nowhere to be stored.)*

- [ ] **IG-29-008 P1** — Create district persistence records for entities and world state that must survive a district transition.
- [x] **IG-29-009 P1** — Create checkpoint snapshot semantics. *(A checkpoint is two halves. The **mission half** (`MissionCheckpointSnapshot`: the state id plus the mission's variables **as they stand once that state's entry actions have run**) is recorded by `PrototypeMission` when it enters a state marked `"checkpoint": true`. The **world half** (`WorldStateSnapshot`: player, vehicle, district) is recorded by `IronGangGame::CaptureMissionCheckpointWorld()` the moment the mission reports a new checkpoint. Both are overwritten by the next checkpoint, survive repeated retries (a retry does not consume one), are discarded by `Reset()` but not by `Retry()`, and round-trip through the save. The world half is all-or-nothing on read: a partial one is dropped rather than half-applied. Placement conventions for mission authors are in `docs/mission-scripting.md`.)*
- [x] **IG-29-010 P1** — Create autosave scheduling that avoids unsafe moments. *(`AutosaveScheduler` (`include/IronGang/Persistence/AutosavePolicy.hpp`) decides when; the game decides what to write. Triggers: a new mission checkpoint, a finished district transition, and a 180-second interval as the backstop between them. Two guarantees carry the design: a request made at an unsafe moment is **held, not dropped**, so an autosave asked for during a cutscene happens the instant it ends; and a 20-second minimum spacing collapses triggers that land together into one save while still deferring the second request rather than discarding it. Autosaves go to their own slot (`…prototype.autosave`) so they never overwrite a save the player made; F9 loads whichever slot is newer via `SaveGame::ChooseMostRecent`, since "load" means "resume". A manual save, a load, or a reset restarts the interval. Covered by `TestAutosaveSchedulingAvoidsUnsafeMoments` and `TestLoadChoosesTheMostRecentSave`.)*
- [x] **IG-29-011 P1** — Create save-blocking reasons and clear UI feedback. *(`SaveBlockReason`/`SaveConditions`/`FindSaveBlockReason` name the four moments where the game holds state the save format does not carry -- a cutscene (the camera is not the gameplay camera), dialogue (the line index is not saved), a district transition (the world being written is the one being unloaded), and getting in or out of the car (the player is neither on foot nor driving). F5 during one of them shows `Can't save: <reason>` on the HUD status line instead of writing a save that would come back wrong or silently doing nothing; autosaves wait instead. `DescribeSaveBlockReason` supplies the player-facing text and is asserted non-empty for every reason.)*
