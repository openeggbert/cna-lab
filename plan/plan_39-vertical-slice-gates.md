# 39. Vertical-slice gates

[Back to master plan](../plan.md)

Define non-negotiable integrated milestones that prevent endless disconnected
engine work. Every gate below assumes the locked project scope: a Mafia-1
(2002)-style campaign built district-by-district and connected by loading
screens (not seamless streaming), Mafia-1-era traffic/police/pedestrian
fidelity (not GTA-scale simulation), `cna-extended` for ECS/scene/collision,
CNA's existing PbrEffect/shadow-mapping/instancing for rendering, no in-house
editor suite, manual MC3 content authoring, and the ~2-4GB RAM / 512MB-1GB
VRAM baked-lighting performance target from `docs/performance-targets.md`.
The full v1 target is multiple districts plus countryside across roughly
15-20 missions — M10 through M12 apply to the FIRST district, then repeat
per additional district (see the expansion gate at the end of this file)
rather than being a one-time final check.

- [ ] **IS-39-011 P0** — Gate M10: the first district's vertical slice uses production-path assets, collision, baked lighting + one dynamic sun + limited shadows, audio, and UI. *(In progress. Locked architecture (research confirmed against CNA's actual source, not assumed -- see below), user explicitly chose the higher-effort option for both baked lighting and audio over a simpler placeholder:*
  - *Production-path assets + collision: already satisfied by M2/M3 (CNJ warehouse/vehicle) plus the existing procedural-AABB collision, which already covers CNJ-rendered objects (colliders are independent of the visual mesh in `PrototypeWorld`). Deriving collision from MC3's own `collision` attribute (confirmed present in `mesh-craft/mc3/mc3.xsd` as a plain string, default "none") is a separate, bigger pipeline task (needs the sidecar/MCB metadata compiler, `plan_10` `IS-10-001`/`002`) and stays deferred.*
  - *Baked lighting (real lightmap textures, not vertex color): confirmed feasible entirely within Iron Shadows, no CNA/cna-extended changes needed. CNA's `DualTextureEffect` (`Microsoft::Xna::Framework::Graphics::DualTextureEffect`) is fully implemented on the SOFTWARE backend (`SoftwareGraphicsBackend.cpp`'s `useDualTexture` path, confirmed by reading the exact blend formula: `finalColor = vertexColor * (texture0 * 2) * texture1 * diffuseColor`, both textures sampled at the SAME uv -- this backend has no genuine 2-UV vertex format, an already-established simplification per its own code comment). Plan: keep `texture0` a flat 50%-gray 1x1 texture (so `texture0*2` = identity, i.e. `finalColor = vertexColor * texture1`), and bake `texture1` as a real lightmap atlas texture computed IN-PROCESS (not an external offline tool/JSON round-trip) directly from `PrototypeWorld::GetBoxes()` at renderer build time -- one flat-shaded tile per box face (ambient floor + `max(0, dot(faceNormal, sunDirection)) * sunIntensity`, clamped), uploaded via `Texture2D(device, w, h)` + `SetData(const Color*, count)` (confirmed both exist). Needs a new vertex format for the static city mesh (`VertexPositionColorTexture`, already exists in CNA) carrying one UV per vertex pointing into the atlas tile for that vertex's face. Scope: the procedural box city only (ground/roads/sidewalks/buildings/lamps) -- MC3-sourced models (warehouse/vehicle) have no lightmap UV channel from the current pipeline and are explicitly out of scope for this pass.*
  - *One dynamic sun + limited shadows: confirmed that `BasicEffect`'s built-in `DirectionalLight0`/`EnableDefaultLighting()` (real XNA API surface) is a NO-OP on the SOFTWARE backend -- its own code comment states "lightingEnabled/fogEnabled remain out of scope for v1 (design decision 6)". Relying on it would silently do nothing and be unverifiable in this no-display environment, so it is NOT used. Instead: a "dynamic sun" is a single shared sun direction/intensity (the same one driving the lightmap bake, for visual consistency) applied as a plain CPU-computed brightness scalar that Iron Shadows itself multiplies into each dynamic actor's (player/vehicle/traffic/pedestrian/police) existing debug-tint color before building/drawing its mesh each frame -- one uniform scalar per actor, not real per-face N-dot-L shading (a documented simplification, matching this session's established pattern). "Limited shadows" -- confirmed the SOFTWARE backend has no shadow-map support at all (CNA's shadow-mapping examples are EasyGL-only, real GPU shader passes) and CNA's effects are fixed hardcoded formulas per backend, not a custom-shader system, so real shadow-mapping is not achievable without modifying CNA itself. Instead: a simple dark, semi-transparent flat ground decal beneath the player and vehicle (confirmed AlphaBlend IS implemented on the SOFTWARE backend, "design decision 7"), a period-appropriate "blob shadow" approximation, not real shadow-mapping.*
  - *Audio: confirmed `SoundEffect::FromStream(std::istream&)` (backed by SDL3_mixer's `MIX_LoadAudio_IO`, which decodes WAV/OGG/MP3 directly -- no XNB/content-pipeline conversion needed, unlike Models) plus `SoundEffectInstance`/`CreateInstance()` for looped/controlled playback (engine hum, ambience) and `Play()`/`Play(volume, pitch, pan)` for one-shots (footstep, horn, siren). Confirmed `NoAudioHardwareException` is thrown if no audio device exists (a real risk in this sandboxed environment) -- wrapped in the same try/catch-with-graceful-fallback convention already used for every other optional asset (Model loads, mission/cutscene files). Per the user's explicit choice, real CC0/royalty-free sound assets are sourced via WebSearch/WebFetch and tracked in `assets/licenses/asset-registry.csv`, not synthesized placeholders.*
  - *UI: `SpriteBatch`/`SpriteFont` (confirmed `Begin`/`DrawString`/`End` API) replace the window-title-only HUD. `SpriteFont`'s constructor is exposed directly for building the glyph atlas ourselves ("CNA has no XNB pipeline" per its own header comment) -- no existing font-building example exists anywhere in `cna`. Decision: a small hand-authored fixed-width bitmap font (not vendoring a new TTF-rasterization dependency like stb_truetype, and not sourcing an external font asset/license) rasterized into a `Texture2D` atlas at startup, matching this project's existing "hand-authored over new dependency" convention (e.g. `test_character.gltf`). Deferred: real proportional typography/localization-ready font tooling (ties into `plan_28`'s own broader scope).*
  - *Implementation order (this session): UI/HUD first (lowest risk, no new asset pipeline) -> dynamic sun + shadow decals (no new asset pipeline) -> baked lightmap (biggest, most novel) -> audio (needs external CC0 asset sourcing). See `NEXT.md` for concrete per-piece progress as each lands.)*
