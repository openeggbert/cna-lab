# wolf-cna — implementation plan

## 0. Project definition

`wolf-cna` is an original retro first-person shooter implemented in **C++23** on top of **CNA**.

The game is inspired by the immediacy and readable grid-like level design of early 1990s FPS games, but it is **not a Wolfenstein 3D source port** and must not contain copyrighted Wolfenstein levels, textures, sounds, characters, names, story, or other proprietary game data.

The renderer is **real polygonal 3D**. There is no software raycaster in the shipping renderer. The initial world can still use a 2D logical cell grid because this is useful for level authoring, collision, AI navigation, doors, secrets, and procedural generation, but the grid is converted to GPU triangle geometry and rendered through CNA.

Working subtitle: **Bunker 1987**. This is only a codename and may be changed later.

### Primary goals

1. Produce a small but complete original retro FPS.
2. Use the project as a demanding integration test for CNA.
3. Keep the game renderer-agnostic: the game talks to CNA, never directly to OpenGL/Vulkan/Direct3D/SDL.
4. Make the codebase easy for AI coding agents to extend in small, verifiable tasks.
5. Avoid asset-license uncertainty by preferring generated original assets at first.
6. Keep a playable build available throughout development.

### Non-goals

- Reimplementing the original Wolfenstein 3D engine byte-for-byte.
- Using Wolfenstein 3D commercial data files.
- Building a general-purpose engine above CNA before the game needs it.
- Adding every planned feature before a vertical slice exists.
- Bypassing CNA when a CNA feature is incomplete. Missing CNA functionality should be documented and, where appropriate, fixed in CNA.

# 1. Technical principles

## 1.1 CNA-only platform and graphics boundary

Game code may use:

- C++ standard library
- CNA public APIs
- project-owned code
- later, carefully approved portable libraries for domains CNA intentionally does not cover

Game code must not directly call:

- SDL2/SDL3
- OpenGL/OpenGL ES
- Vulkan
- Direct3D
- Metal
- platform window APIs
- platform input APIs
- renderer-specific CNA internals

A direct backend call added merely to work around CNA is considered a defect.

## 1.2 Real 3D

The world is represented by triangles.

Initial level representation:

```text
logical grid / level description
            |
            v
      world mesh builder
            |
            v
 VertexBuffer + IndexBuffer
            |
            v
        BasicEffect
            |
            v
       CNA renderer
```

Walls have physical height. Floors and ceilings are polygonal surfaces. Later milestones may add different heights, ramps, platforms, meshes, doors, elevators, props, decals, particles and models.

The grid is a gameplay/authoring structure, not a rendering trick.

## 1.3 Deterministic simulation

Prefer a deterministic fixed gameplay tick eventually (target: 60 Hz) with rendering decoupled where practical.

Random gameplay generation must use an explicit seed. Do not use hidden global randomness for procedural levels or combat outcomes.

## 1.4 Data-oriented simplicity before abstraction

Do not create a giant ECS/framework pre-emptively.

Start with explicit structures:

- `Player`
- `World`
- `Door`
- `Enemy`
- `Projectile`
- `Pickup`
- `Level`
- `GameState`

Refactor only after duplication or scale demonstrates a need.

# 2. Asset and licensing policy

## 2.1 Initial policy

The initial implementation uses **runtime-generated procedural textures**. No external game art is required.

Generated starter textures include:

- brick/wall panel
- floor panel
- ceiling panel

They are generated by project code and therefore do not depend on third-party image files.

## 2.2 Later assets

Allowed categories:

1. assets created specifically for wolf-cna;
2. generated assets whose terms allow redistribution and modification;
3. CC0/public-domain assets;
4. permissively licensed assets after their exact license and attribution requirements are recorded.

Before adding any third-party asset, record:

- asset name;
- author/source;
- exact source URL;
- exact license;
- whether modification is permitted;
- required attribution;
- file paths using the asset.

Maintain this in `THIRD_PARTY.md`.

Do **not** copy Wolfenstein 3D art, maps, audio, logos, characters, weapon sprites, or other proprietary data.

## 2.3 Project license

No license is selected by this starter. Choose and add the repository license before public distribution.

# 5. Gameplay concept

## 5.1 Premise

The player enters an abandoned late-1980s underground research complex controlled by a damaged security computer. The complex was designed as a modular bunker and has begun reconfiguring itself.

This supports intentionally grid-readable early-FPS level design while allowing increasingly impossible geometry and technology later.

## 5.2 Core loop

```text
enter sector
    ->
explore / fight
    ->
find access credential or objective
    ->
unlock deeper area
    ->
collect weapons/resources/secrets
    ->
destroy or bypass sector controller
    ->
exit sector
```

## 5.3 Combat goals

Combat should be fast and readable rather than realistic.

Initial weapon set target:

- sidearm;
- automatic weapon;
- shotgun-like close weapon;
- energy weapon;
- explosive weapon.

Every weapon needs a distinct tactical role.

## 5.4 Enemy archetypes

Initial target:

- guard/drone: basic hitscan or projectile attacker;
- runner: fast melee enemy;
- turret: stationary area denial;
- shield unit: directional defense;
- heavy unit: slow high-health enemy;
- sector boss.

AI does not need sophisticated planning initially. Good spatial behavior, readable telegraphing, hearing/vision, cover-ish decisions, and pathfinding are more valuable.

# 8. Level representation evolution

## Phase A: char grid

Starter:

```text
#################
#P..............#
#.#####.#######.#
#...............#
#################
```

Symbols:

- `#` solid wall
- `.` walkable cell
- `P` player spawn

## Phase B: structured cell data

Example concept:

```cpp
struct Cell {
    MaterialId floor;
    MaterialId ceiling;
    float floorHeight;
    float ceilingHeight;
    WallEdge north;
    WallEdge east;
    WallEdge south;
    WallEdge west;
};
```

This supports different heights while retaining grid authoring.

## Phase C: hybrid level

Grid remains available for navigation/logic while arbitrary mesh objects can be placed in world space.

Do not force arbitrary props and enemies into grid cells.

# 9. Collision plan

## Starter

Horizontal circle against solid grid cells.

Advantages:

- very small;
- robust enough for rectangular walls;
- AI can reuse grid semantics;
- easy to test.

## Next

Move to swept movement:

1. desired displacement;
2. split movement into safe substeps or perform sweep;
3. resolve X/Z separately or with contact normals;
4. preserve sliding;
5. handle moving doors/platforms.

Later vertical movement can use capsule/character-controller semantics.

Do not introduce a full physics engine merely for FPS walking unless the game actually needs one.

Use explicit state machines initially:

```text

 -> Suspicious
 -> Chase
 -> Attack
 -> Search
 -> Chase
```

Perception:

- distance;
- field of view;
- ray/visibility test;
- sound events.

Navigation:

1. direct steering where line-of-sight exists;
2. grid A* for route finding;
3. local collision avoidance only if needed.

Tests should cover unreachable targets and locked-door state changes.

# 17. Definition of a useful CNA finding

wolf-cna exists partly to expose framework gaps.

When a CNA limitation appears, record:

- exact API attempted;
- expected XNA/CNA behavior;
- actual behavior;
- renderer/platform;
- minimal reproduction;
- whether the game can continue without a workaround.

Classify as:

- `GAME`: bug in wolf-cna;
- `CNA-BLOCKER`: required CNA behavior absent/broken;
- `CNA-ENHANCEMENT`: useful but not required;
- `BACKEND`: behavior differs between CNA renderers.

Do not permanently hide a CNA bug inside game code.

- bunker power routing;
- terminals;
- cameras;
- alarms;
- changing level topology;
